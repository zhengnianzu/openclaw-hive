# 队列排队使用说明

队列用来让**多个任务按顺序串行执行**：一个跑完，下一个自动开始。不用自己盯着。

## 一、把任务放进队列

**创建任务 → 高级配置 → 任务队列**，选一个已有队列，或点「新建队列」。

也可以给已经在跑/已完成的任务改归属：在任务列表里把任务加入某个队列。

队列的两个可调参数（新建或编辑时设置）：

| 参数 | 说明 |
|---|---|
| **并发数** | 这个队列同时最多跑几个。默认 1（严格串行）。实际并发还会被全局上限 `QUEUE_MAX_CONCURRENT`（默认 2）封顶。 |
| **长尾跳过** | 可选。开启后，正在跑的任务剩余量降到阈值以下时，允许提前放行下一个。 |

## 二、长尾跳过是什么

一批任务的耗时常常是长尾的：最后几个可能比前面几十个都慢。严格串行时，这段时间只有一台在跑，整体吞吐掉下来。

开启长尾跳过（比如 10%）后，当正在跑的任务**剩余任务数 ≤ 10%** 时，队列会额外放行一个任务。于是峰值并发变成「基础并发 + 1」。

- 阈值可设 1–50%。
- 剩余量按**任务数比例**算，不用时间预测——冷启动没有历史数据也能工作。
- 任务数还没统计出来时不触发。
- 长尾任务结束后，并发自动回落到基础值。

## 三、启动与停止

| 操作 | 行为 |
|---|---|
| **启动**（单个任务） | 队列空闲 → 立即开始；队列被占 → 转「排队中」。**同时把该任务重新排到队尾。** |
| **启动队列** | 把队列里所有「待启动 / 已停止」的任务一起放进排队，按顺序依次执行。 |
| **停止**（单个任务） | 杀进程，状态转「已停止」。**保留队列归属**，下次启动不用重选队列。 |
| **停止队列** | 把「排队中」的任务退回「待启动」。**正在运行的任务不受影响。** |

## 四、状态怎么读

| 状态 | 含义 | 占不占队列槽位 |
|---|---|---|
| 待启动 | 已创建，还没启动 | 否 |
| **排队中** | 在队列里等待前一个结束 | 否 |
| **准备中** | 正在下载 OBS 配置、打包、统计任务数 | **是** |
| **运行中** | hive.py 已拉起 | **是** |
| 已完成 / 已结束 | 结束（有失败任务时显示「已结束」） | 否 |
| 已停止 | 被手动停止 | 否 |
| 失败 | 准备或启动失败，原因见 `error_summary` | 否 |

> 「准备中」也算占槽位。因为下载/打包可能要好几分钟，如果这时放行下一个，串行就失效了。

## 五、排队名次怎么看

任务列表和任务详情里显示的「队列位置」是**该队列里排队中的第几名**，不是数据库里的序号。

内部序号只增不减（重新启动会排到队尾），所以你会看到 `1, 2, 3, 7, 8` 这样的空洞——这是正常的，界面显示的始终是重算后的名次。

## 六、失败了怎么办

准备阶段失败（比如 `user_config_dir` 指向的 OBS 路径不存在）会标为**失败**，而不是退回「待启动」。

这是有意的：

- 退回「待启动」会让你以为「没启动成功」，反复点、反复失败。
- 「启动队列」**不会**自动拉起失败的任务——否则一条配置错误的任务会把整条队列堵死。

正确做法：在任务列表点开失败的实例看错误信息，修好配置后**单独点「启动」**重试。重试会自动清空上一次的错误。

队列列表上会显示失败任务数，避免它们「隐身」。

## 七、常见问题

**Q：任务一直卡在「准备中」怎么办？**
系统有看门狗：超过 `PREPARE_TIMEOUT_SECONDS`（默认 30 分钟）仍未拉起进程的，会标记为失败并放行下一个。如果确实需要更长时间，可以调大这个配置（改 `.env` 后要重启后端）。

**Q：后端重启了，排队的任务会丢吗？**
不会。启动时会扫描所有还有排队任务的队列，兜底调度一次，继续跑。

**Q：不同队列会互相影响吗？**
不会。每个队列独立调度，只受全局并发上限约束。

**Q：为什么队列里有任务，但一个都没在跑？**
检查是否有任务处于「失败」状态但没被处理，或者看是否有「准备中」的实例卡住。队列列表的失败计数能提示前者。
